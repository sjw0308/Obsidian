# 운영체제 중간고사 최종본

> **시험 직전용 요약.** 정리 노트 9개와 모의시험 1~4회 오답을 반영했다. 한국어 설명에 시험에서 쓰는 영어 용어를 함께 적었다. 계산·구현은 강의의 교육용 모델을 기준으로 하며, 문제에 주어진 규칙이 우선이다.
>
> **3분 남으면 0번만 → 10분이면 0번과 굵은 문장 → 시간이 남으면 각 절의 표·예시를 확인.**

## 0. 들어가기 전 반드시 확인할 12가지

1. **Turnaround = 완료 − 도착**, **Response = 최초 실행 − 도착**. 완료 시각 자체가 turnaround는 아니다.
2. **Quantum은 최대 연속 실행량**이다. 남은 CPU 작업량이 1이면 quantum이 2여도 1만 실행하고 끝난다.
3. **I/O 완료 → Ready/Runnable**, 즉시 Running은 아니다.
4. **커널 진입 ≠ 프로세스 전환.** Syscall 후 같은 프로세스로 돌아올 수 있다. 타이머 interrupt는 syscall을 강제로 호출하는 것이 아니다.
5. 같은 프로세스의 스레드는 **주소공간·열린 파일 자원 공유**, **PC·레지스터·스택은 별도**다.
6. **Coherence ≠ atomicity.** Cache가 일관돼도 `x++` 전체는 원자적이지 않다.
7. **Guard는 flag·대기 큐를 보호한다.** 그 자체가 timer interrupt나 context switch를 금지하지 않는다.
8. **Consumer는 full을 기다리고 empty를 돌려준다.** Producer는 empty를 기다리고 full을 돌려준다.
9. **Hold and wait = 보유하며 추가 대기. No preemption = 강제 회수 불가.** 스스로 해제할 수 없다는 뜻이 아니다.
10. **Deadlock: 대기하며 멈춤 / Livelock: 움직이지만 진전 없음 / Starvation: 특정 작업이 계속 밀림.**
11. **Amdahl: speedup = 1/\[S+(1−S)/N], 무한 코어 상한 = 1/S.** 실행시간과 speedup을 모두 확인한다.
12. 비용이 0이면 **합산 idle = 코어 수 × 전체 makespan − 총 CPU 요구량**. 병합 전에는 **모든 필요한 부분 결과의 완료·가시성**을 보장한다.

## 1. Process / kernel / context switch

### 1.1 프로그램과 스레드

| 항목 | 핵심 |
|---|---|
| Program / Process | 프로그램은 실행 코드·데이터, 프로세스는 실행 중인 인스턴스 |
| 프로세스의 추상화 | 독립적인 logical control flow, private virtual address space |
| 같은 프로세스 스레드의 공유 | 코드·전역변수·힙을 포함한 주소공간, 열린 파일 자원 |
| 스레드별 상태 | PC, 레지스터, 스택. 다른 스레드가 주소를 알면 스택 메모리에도 접근할 수 있으나 각 실행 흐름의 스택은 따로 유지 |
| 스레드 전환 | 실행 상태 교체. 같은 프로세스라면 주소공간은 유지 |
| Policy / Mechanism | Scheduling은 누구를 실행할지 결정, context switch는 상태 저장·복원으로 실제 전환 |

**컴파일 순서**

`C(.c) → compiler → assembly(.s) → assembler → object(.o) → linker(+libraries) → executable`

| ELF 영역    | 내용                                        |
| --------- | ----------------------------------------- |
| `.text`   | 기계어 코드                                    |
| `.rodata` | 읽기 전용 데이터                                 |
| `.data`   | 초기화된 전역·정적 데이터                            |
| `.bss`    | 미초기화/0 초기화 전역·정적 데이터. 위 표의 분류는 강의의 일반적 모델 |

낮은 우선순위 확인: OS는 자원 가상화·동시성 제어·영속성 지원을 제공하며 성능·격리·신뢰성을 함께 고려한다.

작은 확인: ISA는 소프트웨어가 보는 명령·상태의 규약, microarchitecture는 그 구현이다. PC·레지스터·condition codes는 실행 상태다. `fork`는 새 프로세스 생성, `exec`는 현재 프로세스의 실행 이미지 교체다.

### 1.2 상태 전이

```text
Ready/Runnable --dispatch--> Running
Running --preemption/yield--> Ready/Runnable
Running --blocking I/O/wait--> Blocked
Blocked --I/O completion/wakeup--> Ready/Runnable
```

- **Ready:** 실행할 조건은 갖췄지만 CPU를 받지 못함.
- **Blocked:** I/O·조건 등을 기다려 아직 실행할 수 없음.
- Block된 시간도 완료까지의 경과시간인 turnaround에는 포함된다.

### 1.3 Limited Direct Execution (LDE)

**목표: 사용자 코드는 CPU에서 직접 실행해 빠르게 처리하되, 권한과 제어권 회수는 OS가 통제한다.**

```text
User 실행 → syscall/trap → 통제된 kernel 진입 및 복귀 상태 저장
→ kernel stack에서 처리 → 복귀 상태 복원 → return-from-trap → User 실행
```

- User mode는 특권 동작이 제한되고, kernel mode는 OS의 특권 동작을 수행한다.
- 사용자 PC·SP 등의 복귀 상태와 커널 실행 context는 역할이 다르다. **“매 진입마다 PCB 전체를 저장한다”로 외우지 않는다.**
- Kernel stack은 커널 처리의 호출·지역변수·저장 상태에 사용한다. 사용자 스택 바로 아래에 붙어 있어야 하는 것은 아니다.
- **Cooperative:** 작업이 syscall·yield 등으로 제어권을 넘겨야 한다. 무한 루프가 자발적으로 넘기지 않을 수 있다.
- **Timer interrupt:** 작업의 협조 없이 kernel이 제어권을 얻는다. 스케줄러가 필요하면 다른 작업으로 전환한다.

| 혼동하기 쉬운 것                     | 구분                                      |
| ----------------------------- | --------------------------------------- |
| Syscall vs interrupt          | 프로그램의 서비스 요청 vs 하드웨어 사건에 의한 진입. 타이머는 후자 |
| Mode switch vs process switch | user/kernel 권한 전환 vs 실행 프로세스 교체         |
| Trap/interrupt vector table   | 사건 종류에 맞는 진입 핸들러 선택                     |
| Syscall dispatch table        | syscall 번호에 맞는 서비스 함수 선택                |

**반례 한 문장:** “짧은 시스템 호출을 처리하고 같은 프로세스로 복귀하면 모드 전환은 있으나 프로세스 전환은 없다.”

## 2. Scheduling: 선택 규칙과 계산

### 2.1 시간 지표와 풀이 순서

$$
T_{turnaround}=T_{completion}-T_{arrival},\qquad
T_{response}=T_{first\ run}-T_{arrival}
$$

- 예: 도착2, 최초실행5, 완료11 → turnaround9, response3.
- CPU만 사용하는 단순 문제에서 waiting = turnaround − CPU 요구량. I/O가 있으면 대기시간을 무엇으로 정의했는지 확인한다.
- **도착·I/O 완료·작업 종료·quantum 만료 시각마다 ready queue와 남은 시간을 갱신한다.**
- 동률, 같은 시각의 도착/재삽입 순서, overhead, 선점 후 남은 quantum은 **문제 규칙**을 따른다.
- 답안은 **타임라인 → 최초실행/완료 시각 → 지표 → 평균** 순으로 작성한다. 묻는 중간 상태도 생략하지 않는다.

### 2.2 기본 정책

| 정책 | 선택 기준 | 선점 | 핵심 주의 |
|---|---|---|---|
| FIFO/FCFS | Ready queue에 먼저 온 작업 | 보통 비선점 | 긴 작업 뒤 짧은 작업이 밀리는 convoy effect |
| SJF | 현재 ready 작업 중 가장 짧은 작업/다음 CPU burst | 비선점 | 미래의 짧은 작업을 기다리려고 일부러 idle하지 않는다(문제에 별도 규칙이 없다면) |
| STCF/SRTF | 현재 남은 CPU 시간이 가장 짧은 작업 | 선점 | 새 도착·I/O 복귀 때 현재 작업의 **남은 시간**과 비교 |
| RR | Ready queue 순서대로 최대 quantum | 선점 | 실제 실행량=min(quantum, 종료/차단까지 시간) |

- RR quantum↓ → 일반적으로 response 개선, 전환 횟수·overhead 비중↑.
- Quantum이 충분히 크고 모든 작업이 첫 배정에서 끝나면 FIFO와 같은 실행 순서가 된다.
- **I/O 동안 해당 작업은 ready 선택 대상에서 빠진다.** 복귀하면 정책에 맞춰 재진입한다.

### 2.3 MLFQ

- 높은 큐 우선, 같은 큐는 RR, 신규 작업은 보통 가장 높은 큐.
- CPU 할당량 소진 시 강등. 높은 큐는 보통 짧은 quantum, 낮은 큐는 긴 quantum.
- 낮은 큐 작업 실행 중 높은 큐 작업이 ready가 되면 높은 큐가 우선한다.
- **같은 큐에 작업이 새로 왔다고 현재 quantum이 자동 종료되는 것은 아니다.**
- **Priority boost:** 낮은 큐 starvation을 완화하고, CPU 중심에서 interactive로 성격이 바뀐 작업에 새 기회를 준다.
- 계산 전 확인: 큐별 quantum/총 할당량, 강등 시점, boost 시각·정렬, 선점 후 잔여 quantum 규칙.

### 2.4 Lottery와 stride

| Lottery | Stride |
|---|---|
| Runnable ticket 중 균등 추첨 | 최소 pass 작업 선택 |
| 기대 점유율 = 내 tickets / runnable 총 tickets | stride = K/tickets |
| 기대 당첨 횟수 = 추첨 수 × 확률 | 실행 후 선택 작업의 pass += stride |
| 유한 횟수의 정확한 비율은 보장하지 않음 | 주어진 상태·동률 규칙에서 결정적 선택 |

- **티켓이 많을수록 stride는 작다.**
- Block된 작업의 티켓을 추첨에 포함하는지 확인. 기본 계산은 runnable 작업만 대상이다.
- Ticket currency는 그룹 내부 비율을 전역 티켓으로 환산한다. Transfer는 다른 작업에 임시 양도, inflation은 티켓 수 증감이다.
- Stride 신규 pass를0으로 넣으면 기존 값에 따라 한동안 신규 작업만 선택될 수 있다. 현재 runnable 최소 pass에 맞추는 등의 보정이 필요하다.
- 동률은 자동으로 이름순이 아니다. 문제에서 정한 규칙을 따른다.

### 2.5 CFS: 강의의 교육용 모델

$$
\Delta vruntime_i=\frac{weight_0}{weight_i}\times\Delta runtime_i
$$

- **최소 vruntime 선택.** 선택된 작업만 실제 실행한 만큼 vruntime이 증가한다.
- Nice↓ → weight↑ → vruntime 증가 속도↓ → 더 많은 실제 CPU 시간을 받을 수 있다.
- 예: 기준1024, weight2048 작업이4ms 실행 → vruntime은2 증가.
- 같은 weight n개일 때 단순 계산:

$$
slice=\max\left(\frac{sched\_latency}{n},min\_granularity\right),\qquad
순환시간\approx n\times slice
$$

- n=8, latency20, min3 → slice3ms, 순환24ms. **순환시간이 latency와 반드시 같지는 않다.**
- 신규 작업 vruntime을 무조건0으로 두지 않고 현재 기준 최소값 부근으로 보정한다는 원리를 기억한다.
- 강의의 CFS는 vruntime 기준 red-black tree를 사용한다. 삽입·삭제 등 유지 비용은 O(log n). **왼쪽 끝 노드가 캐시되어 있으면 최소 작업 조회 자체는 O(1)일 수 있다.**
- 위 slice 식은 같은 weight를 가정한 교육용 계산이다. 실제 런타임과 vruntime을 혼동하지 않는다.

## 3. Lock / semaphore / deadlock

### 3.1 Race와 원자성

**`x++ = load → add → store`. 각각이 원자적이어도 전체가 원자적인 것은 아니다.**

예: x=0, 두 스레드가 각각 한 번 증가.

`T1 load0 → T2 load0 → T1 add/store1 → T2 add/store1` → 최종1.

- **Race condition:** 실행 순서에 따라 공유 상태의 결과가 달라짐.
- **Critical section:** 공유 상태에 대한 충돌 가능한 접근 구간.
- **Mutual exclusion:** 한 번에 한 스레드만 해당 보호 구간에 진입.
- 같은 락으로 **load부터 store까지 전체**를 보호하거나 원자적 증가 연산을 사용한다.
- Interrupt disable은 해당 CPU에만 적용된다. 다른 코어의 공유 메모리 접근까지 막지 않는다.

### 3.2 락 구현별 핵심

| 방식 | 동작 | 남는 문제 |
|---|---|---|
| Test-and-set (TAS) | 원자적으로 이전 값을 반환하고 새 값 저장 | FIFO 공정성 없음, spinning |
| Compare-and-swap (CAS) | 예상 값과 같으면 새 값으로 원자적 교체 | 반환 규약 확인; CAS 사용만으로 모든 알고리즘이 lock-free인 것은 아님 |
| Ticket lock | FetchAndAdd로 번호 발급, turn이 내 번호일 때 진입 | 번호 순서는 공정하지만 spinning 비용은 남음 |
| Yield | 기다리는 대신 CPU를 양보하여 runnable 상태로 남음 | 전환 비용, 재경합·starvation 가능 |
| Sleeping lock | 큐에 등록하고 block, 소유자가 깨움 | 큐 보호와 lost wakeup 방지 필요 |

```text
TAS lock: while (TestAndSet(&flag,1) == 1) {}
unlock: flag=0
Ticket: my=FetchAndAdd(ticket); wait until turn==my; unlock increments turn
```

이 코드는 원자성·가시성을 제공하는 강의 모델의 의사코드다. **CAS는 이전 값을 반환하는 버전과 성공 여부를 반환하는 버전이 있으므로 문제의 정의를 먼저 읽는다.**

### 3.3 Guard, park, setpark

- Guard는 **flag와 대기 큐의 짧은 조작**을 보호한다. 전체 임계 구역의 소유권과는 다르다.
- Guard를 잡은 스레드도 선점될 수 있다. 다른 스레드는 같은 guard 보호 구간에 동시에 못 들어간다.
- Lost wakeup:

`대기 큐 등록 → guard 해제 → 상대가 unpark → 내가 park → 알림을 놓쳐 잠듦`

- **Setpark 위치: 큐 등록 후, guard 해제 전.** 그 후 unpark가 먼저 오면 다음 park가 잠들지 않게 기억한다.
- **Direct handoff:** 대기자가 있으면 그 스레드로 락을 넘기므로 flag=1 유지. 0으로 만들면 새 진입자가 락을 가로챌 수 있다.

### 3.4 Semaphore: 허가를 세는 도구

- `wait`: 허가를 하나 획득. 없으면 대기.
- `post`: 허가를 하나 반환/추가. 대기자가 있으면 하나를 깨움.
- 강의의 음수 카운터 모델은 wait 때 감소하고 음수면 대기한다. 값이 −k이면 대기자k명. 실제 API가 항상 음수를 외부에 표시한다는 뜻은 아니다.
- 초기값1은 상호배제에 활용, 초기값0은 완료 신호에 활용.
- 완료 신호: `s=0; 자식은 결과 기록 후 post; 부모는 결과 사용 전 wait`.
- **Post가 먼저여도 허가가 남는다.** 단순히 알림을 버리는 park/unpark 모델과 구분한다.

**Bounded buffer에서 가장 자주 뒤집힌 부분**

| 세마포어 | 의미 | 초기값 |
|---|---|---|
| empty | 생산 가능한 빈 슬롯 허가 | N |
| full | 소비 가능한 데이터 허가 | 0 |
| mutex | 버퍼 조작의 상호배제 | 1 |

```text
Producer: wait(empty) → wait(mutex) → put → post(mutex) → post(full)
Consumer: wait(full)  → wait(mutex) → get → post(mutex) → post(empty)
```

**허가를 먼저 기다리고, 버퍼를 잠깐 잠그고, 작업 후 반대 허가를 돌려준다.**

Mutex를 먼저 잡고 자원 허가를 기다리면, 가득 찬 버퍼에서 producer가 mutex 보유/empty 대기 → consumer가 mutex 대기 → 아무도 비울 수 없는 deadlock이 가능하다.

### 3.5 Reader-writer와 철학자

- 여러 reader는 동시 진입 가능. Writer는 다른 reader/writer와 배타적이어야 한다.
- 첫 reader가 write_lock 획득, 마지막 reader가 해제.
- **Readers 증감과 첫·마지막 판정을 함께 보호**해야 한다.
- Reader 우선 구현에서 reader가 계속 겹쳐 들어오면 count가0이 되지 않아 writer가 굶을 수 있다.
- Dining philosophers: 모두 같은 방향 포크를 먼저 잡으면 원형 대기 가능. 한 명의 순서를 뒤집으면 이 원형 대기를 끊을 수 있다.
- **Deadlock 방지와 개별 작업의 starvation 방지는 별개다.**

### 3.6 Deadlock: 조건을 실행 상황에 대응시키기

| 필요조건 | 정확한 뜻 |
|---|---|
| Mutual exclusion | 자원을 동시에 공유할 수 없어 단독 소유 |
| Hold and wait | 일부 자원을 가진 채 추가 자원을 기다림 |
| No preemption | 소유자에게서 자원을 강제로 회수할 수 없음 |
| Circular wait | 각 작업이 다음 작업이 가진 자원을 기다리는 순환 |

- 네 조건 중 하나라도 성립하지 않으면 해당 자원 데드락을 피할 수 있다. 자원 인스턴스가 여러 개인 일반 문제에서는 단순히 cycle을 봤다는 사실만으로 단정하지 않는다.
- 예: P가 X를 가지고 Q의 Y를 기다리지만 Q는 아무것도 기다리지 않고 끝난다 → cycle 없음, deadlock 아님.

| 대응 | 원리 / 대가 |
|---|---|
| Prevention | 전역 락 획득 순서 등으로 필요조건을 구조적으로 제거 |
| 전역 순서 | 모두 L1<L2<L3 순으로 획득 → circular wait 제거 |
| 필요한 자원 일괄 획득 | 일부 보유 상태에서 추가 대기를 피함 → hold and wait 제거, 동시성·이용률 손해 가능 |
| Trylock 실패 시 해제·재시도 | 보유한 채 기다리지 않지만 livelock 가능. 무작위 backoff는 완화책이며 절대적 공정성 보장은 아님 |
| Avoidance | 자원 요구 등에 대한 정보를 바탕으로 할당 후에도 안전하게 완료 가능한 상태 유지 |
| Detection & recovery | 발생을 허용한 뒤 탐지하고 작업 종료·복구 등으로 해소 |

**Deadlock은 기다려서 멈춤, livelock은 계속 시도하지만 진전 없음, starvation은 다른 작업은 진행하는데 특정 작업만 계속 밀림.**

## 4. Multicore: 분할·성능·스케줄링

### 4.1 병렬성 종류와 결과 병합

| 개념 | 판단 기준 |
|---|---|
| Concurrency | 여러 실행 흐름의 진행이 시간상 겹침. 단일 코어의 interleaving으로도 가능 |
| Parallelism | 여러 실행 흐름을 실제로 동시에 실행. 여기서는 여러 코어가 필요 |
| Data parallelism | 데이터를 나누고 각 조각에 같은 연산 |
| Task parallelism | 서로 다른 작업을 나누어 실행 |
| Hybrid | 데이터 분할과 작업 분할의 결합 |

- B가 A의 출력을 필요로 하면 **A 완료 후 B 실행**이라는 의존성이 있다.
- 분할 작업끼리 독립적이어도 병합은 모든 필요한 결과가 끝난 뒤 시작한다.
- **Join·완료 세마포어 등으로 완료와 메모리 가시성을 보장**한다. “데이터가 독립적이다”만으로 병합 시작 조건이 충족되지는 않는다.

### 4.2 Amdahl: 고정 작업 크기, 이상적 병렬 분할

$$
T_N=T_1\left(S+\frac{1-S}{N}\right),\qquad
Speedup_N=\frac{T_1}{T_N}=\frac{1}{S+(1-S)/N}
$$

$$
Speedup_{\infty}=\frac1S\quad(S>0)
$$

- S는 **단일 코어 실행시간 중 직렬 부분 비율**. 20%는0.2로 넣는다.
- 이상적 분할·추가 비용0이면 위 값과 같고, 추가 비용이 있으면 실제 speedup이 더 작아질 수 있다.
- 추가 elapsed overhead H(N)이 주어지면 `T_N=T_1[S+(1−S)/N]+H(N)`으로 계산한다. Speedup 분모에 시간을 빼먹지 않는다.
- 여러 영역이 서로 다른 코어 수로만 확장되면 **영역별 시간을 나누어 더한다.**

**확인 예:** T1=100, S=0.2, N=4 → T4=40, speedup2.5, 무한 코어 상한5.

**역산 예:** S=0.2에서 speedup≥4 → `0.2+0.8/N≤0.25` → N≥16.

**실수 방지:** `10/3≈3.33 > 40/13≈3.08`. 두 수를 맞게 구하고 결론을 뒤집지 않는다. 직렬 비율 축소가 코어 추가보다 항상 좋은 것은 아니며 주어진 값을 비교한다.

### 4.3 Cache와 큐 구조

| 개념 | 핵심 |
|---|---|
| Cache coherence | 여러 cache의 같은 메모리 위치에 대한 일관성. 복합 연산의 원자성을 대신하지 않음 |
| Cache affinity | 이전에 실행하던 코어의 따뜻한 cache를 재사용하는 이점 |
| SQMS | 공유 큐 하나. 부하 배분이 단순하지만 큐 보호·직렬화 경합과 작업 이동에 따른 locality 손실 가능 |
| MQMS | 코어별 큐. 로컬 접근 경합은 줄지만 큐별 남은 일이 달라 부하 불균형 가능 |
| Migration | 작업을 다른 코어로 이동. Idle 코어 활용과 cache 재가열 비용 사이의 절충 |
| Work stealing | 일이 없는 코어가 다른 큐에서 작업을 가져옴. 큐 탐색·동기화·cache 비용이 있음 |

- **MQMS가 모든 경로에서 자동으로 lock-free인 것은 아니다.** Owner와 stealer가 같은 큐를 동시에 수정할 수 있다.
- Affinity를 지키면 일부 코어가 놀 수 있고, 부하를 나누면 cache miss가 늘 수 있다.
- Steal 가능한 대상을 확인한다. 문제에서 실행 중인 작업의 이동을 금지했다면 대기 큐 작업만 옮긴다.

### 4.4 Makespan / aggregate idle / utilization

**Makespan은 모든 작업이 끝나는 전체 완료시각**이다. 각 CPU가 자기 일을 끝낸 시각과 구분한다. 측정은 시각0부터라고 가정한다.

$$
Aggregate\ idle=N\times Makespan-\sum_i CPU_i
$$

별도 비용이 없을 때의 식이다. 전환·migration 비용이 있으면 `총 용량 = 유용 실행 + 비용 실행 + idle`로 나눈다.

$$
Useful\ utilization=\frac{\sum_i CPU_i}{N\times Makespan}
$$

**4회 오답 검산:** 총 CPU 요구량16, 코어2.

- 이동 전 makespan12 → 합산 idle=24−16=8.
- 이동 후 makespan8 → 합산 idle=16−16=0.
- 두 코어가 모두8씩 일했다고 idle이8인 것이 아니다. **Idle은 일하지 않은 시간**이다.
