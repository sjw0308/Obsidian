
1. 프로세스와 커널 진입
	1. fork는 자신과 같은 자식 process를 만드는 것이고, exec은 현재 프로세스에 새로운 실행파일을 덮어쓰는 것이기에 exec 호출을 성공해도 프로세스의 개수는 변하지 않는다. 
	2. coorperative방식은 유저 프로세스가 syscall등을 부르지 않고, 제어권을 OS에게 주지 않으면 해당 제어권을 가져올 수 있는 방법이 없다는 한계가 있다. 따라서 timer interrupt를 발생시켜서 강제로 trap한 후 scheduling할 필요가 있다. 
	3. user->kernel->user의 모드 전환은 일어나지만 프로세스 전환은 발생하지 않는다. 
2. SJF, STCF
	1. SJF: A 6ticks -> C 1tick -> B 2ticks
	   STCF: A 1tick -> B 2ticks -> C 1tick -> A 5ticks
	2. SJF: A=6, B=9, C=7, avg=22/3
	   STCF: A=9, B=3, C=4, avg=16/3
	3. A=0, B=0, C=1
3. MLFQ
	1. --pass--
	2. 기대비율: 25%, 랜덤하게 정해서 배정하기 때문에 정확히 한 번 배정되지 않을 수 있다.
	3. 이미 작업중인 process들의 starvation현상이 일어난다. 따라서 현재 pass value 중 최솟값으로 설정하면 된다.
4. ticket lock
	1. T1이 load -> context switch -> T2가 load, add, store -> T1이 add, store. load-add-store전체가 포함되도록 락을 걸어야 한다. 
	2. T1 = 0, T2 = 1, T3 = 2, ticket lock ticket=3/turn=0, 최초 진입자: T1, 첫 unlock 후 turn = 1
	3. ticket lock 또한 loop를 돌면서 thread가 lock을 기다리는 busy wait 성능문제가 있다. 
5. deadlock, semaphore
	1. 초기값 = 0/ 부모가 자식을 만들고 wait -> 자식이 완료한 후 post
	2. empty = N, full=0, mutex = 1, producer가 mutex를 잡고 empty를 기다리면, consumer가 mutex를 기다리면서 둘이 deadlock을 형성하게 됨
	3. L1, L2라는 mutex가 존재. 서로 하나의 lock을 잡고 놓지 못함. 강제회수가 불가능함. T1은 L1을 잡고 L2를 T2는 L2를 잡고 L1을 기다리는 circular wait형태임. T1, T2중 하나가 lock을 잡는 순서를 바꾸면 deadlock이 발생하지 않음
6. 병렬성
	1. concurrency는 우리가 보이게 동시에 실행하는 것 처럼 보이는 것이고 parallelism은 실제로 여러게의 core를 통해서 동시에 실행되는 것이다. 단일 코어에서도 concurrency는 가능하다. 
	2. 첫번쨰는 data parallelism, 두번째는 ~~ 이다. 
	3. A와 B는 서로 dependent이므로 다른 코어에서 동시에 시작할 수 없다. A가 끝난 후 B를 수행해야 한다.

8. SQMS, MQMS
	1. SQMS는 같은 job이 같은 process로 들어가지 않을 수 있기 때문에 Cache affinity를 떨어뜨리고 이 점이 코어수 증가시 overhead로 작용할 수 있다.
	2. 두 개 이상의 processor가 같은 queue에 접근하면 lock을 이용해야 해서 병렬성이 떨어진다. 따라서 다른 프로세서 별로 다른 queue를 사용한다. 그러나 그런경우 하나의 processor에만 일이 집중되는 부하 불균형 문제가 발생할 수 있다. 
	3. 그래도 여전히 필요하다. 같은 processor에서는 여전히 concurrency이슈가 있기 때문이다.
