## 상세 채점·피드백

### 1. OS와 실행 파일: 0.5 / 4점

- **(가): 채점 제외.**
- **(나): 0.5 / 4점.** 컴파일러와 어셈블러의 출력 순서가 뒤바뀌었습니다. 링커가 라이브러리를 결합해 실행 파일을 만든다는 취지는 인정해 단계 배점 2점 중 0.5점을 부여했습니다. 나머지 단계 및 ELF 영역은 틀리거나 누락되었습니다.

올바른 흐름:

`C 소스(.c) → 컴파일러 → 어셈블리(.s) → 어셈블러 → 오브젝트(.o) → 링커 → 실행 파일`

초기화된 전역변수는 `.data`, 초기화되지 않은 전역변수는 `.bss`입니다. 이 두 영역은 각각 1점인데 답에 없어 0점입니다.

### 2. 프로세스와 제어권: 5 / 6점

- **(가): 채점 제외.**
- **(나): 3 / 3점.** I/O 요청에 따른 Blocked 전환과 I/O 완료 후 Runnable 전환이 정확합니다. 여기서 Runnable은 문제의 Ready와 같은 의미로 인정합니다.
- **(다): 2 / 3점.** 타이머 인터럽트를 통해 프로그램의 자발적 호출 없이 커널로 제어권을 넘긴다는 핵심은 맞습니다. 다만 **인터럽트가 강제로 syscall을 발생시키는 것은 아닙니다.** 타이머 인터럽트 자체가 커널의 인터럽트 핸들러 진입을 유발하며, 이후 OS가 스케줄링을 수행할 수 있습니다. syscall과 interrupt를 혼동한 부분에서 1점 감점했습니다.

### 3. 스케줄링 계산: 20 / 20점

- **(가): 8 / 8점.** SJF와 STCF의 순서 및 실행 길이가 모두 정확합니다. 구간 경계 대신 연속 실행 길이로 적은 답도 동일하게 인정합니다.
- **(나): 8 / 8점.** 두 정책의 작업별 turnaround와 평균이 모두 정확합니다.
- **(다): 4 / 4점.** 작업별 response가 모두 정확합니다. 추가로 계산한 평균도 맞습니다.

### 4. MLFQ와 RR: 8 / 10점

- **(가): 4 / 4점.** 짧은 slice에 따른 response 개선과 context switch 비용 증가를 정확히 설명했습니다.
- **(나): 3 / 3점.** 낮은 우선순위 작업의 starvation과 작업 성격 변화, boost의 필요성을 잘 설명했습니다.
- **(다): 1 / 3점.** CPU 사용량을 바탕으로 강등한다는 방향은 맞아 1점을 인정합니다. 다만 `사용시간 / timeslice`가 1에 가까운지만 보면, 작업이 임계값보다 일찍 양보하는 방식으로 계속 회피할 수 있습니다. **I/O를 요청해도 사용량을 초기화하지 않고, 같은 큐에서 소비한 CPU 시간을 여러 실행에 걸쳐 누적한다**는 조건이 필요합니다.

정답 예: “같은 우선순위에서 사용한 CPU 시간을 누적하고, I/O로 양보해도 누적량을 유지한다. 총 할당량을 소진하면 강등한다.”

### 5. Race condition: 8.5 / 10점

- **(가): 4 / 4점.** 제시한 실행 순서에서도 A가 저장한 오래된 값이 B의 결과를 덮어써 최종값이 1이 됩니다. 모범답안과 순서가 달라도 올바른 interleaving입니다.
- **(나): 3 / 3점.** 가능한 값 1, 2와 보호해야 할 load-add-store 전체 구간을 정확히 지목했습니다. 실제 보호 시에는 전체를 같은 락의 획득·해제로 감싸면 됩니다.
- **(다): 1.5 / 3점.** 별도 저장 상태인 PC와 레지스터는 정확하여 해당 부분 1.5점을 부여했습니다. 공유 자원 두 가지는 ‘같은 가상 주소공간’과 ‘열린 파일 자원’ 등으로 써야 합니다. `memory`는 공유 주소공간을 뜻했을 수 있지만, `CPU와 memory`만으로는 스레드가 공유하는 프로세스 자원 두 가지를 정확히 특정하지 못해 공유 자원 부분 1.5점은 부여하지 않았습니다.

### 6. 하드웨어 락: 9 / 10점

- **(가): 4 / 4점.** 획득 반복문은 맞습니다. 해제에 `TestAndSet(&l->flag, 0)`을 사용한 것도 원자적으로 flag를 0으로 바꾸므로 정답으로 인정합니다. 반환값을 사용하지 않으며, 문제에서 가정한 메모리 가시성을 전제로 합니다. `flag=0`보다 강한 원자 연산을 사용했다는 이유로 감점하지 않았습니다.
- **(나): 2 / 3점.** 먼저 기다린 작업에 먼저 락을 준다는 FIFO 공정성 설명은 맞습니다. 다만 **대기 중 spinning으로 CPU 시간을 소비하는 비용이 남는다**는 답이 누락되어 1점 감점했습니다. 구현은 실제 대기 큐 대신 ticket 번호와 turn 값을 사용한다는 점도 구분해 두세요.
- **(다): 3 / 3점.** 다른 CPU에서 공유 영역에 동시에 접근할 수 있다는 설명이 정확합니다.

### 7. 세마포어와 bounded buffer: 4 / 7점

- **(가): 3 / 3점.** 초기값이 모두 정확합니다.
- **(나): 채점 제외.**
- **(다): 1 / 4점.** deadlock이라는 결과는 맞아 1점을 인정합니다. 문제는 ‘어떤 상황에서’ 발생하는지도 요구했으므로 상황과 대기 관계 설명이 필요합니다.

정답 예: “버퍼가 가득 찼는데 producer가 mutex를 잡은 채 empty를 기다린다. consumer는 mutex가 없어 버퍼를 비울 수 없다. producer는 consumer가 empty를 늘려 주기를 기다리고, consumer는 producer가 mutex를 풀기를 기다려 deadlock이 발생한다.”

### 8. 데드락: 10 / 15점

- **(가): 6 / 8점.** Mutual exclusion, no preemption, circular wait는 각 2점을 인정합니다. Hold and wait에 대응시킨 ‘잡고 있는 락을 놓을 수 없다’는 설명은 no preemption과 중복됩니다. 이 조건은 **한 자원을 보유한 상태에서 추가 자원을 기다린다**는 뜻입니다. 추가 자원 대기를 조건 2의 설명에 명시하지 않아 해당 2점을 감점했습니다.
- **(나): 4 / 4점.** 모든 스레드가 전역 순서에 맞춰 락을 획득하도록 하는 해결법이 정확합니다. 제거하는 조건을 이름으로 쓰지는 않았지만, 제시한 순서 규칙이 circular wait를 막는다는 의미를 인정했습니다.
- **(다): 0 / 3점.** 재실행 비용과 malloc 정리 부담은 실제 고려사항이지만, 이 문항의 ‘즉시 재시도’에 남는 핵심 진행 문제는 **livelock**입니다. 두 스레드가 락을 잡았다가 실패해 풀기를 반복하며 둘 다 작업을 진행하지 못할 수 있습니다. Deadlock은 기다리며 멈춘 상태이고, livelock은 계속 동작하지만 진전이 없는 상태입니다.

## 우선 복습할 내용

1. **컴파일·어셈블·링크 순서와 ELF 영역:** 1-(나)에서 3.5점 감점.
2. **동기화의 진행 문제:** bounded buffer의 구체적 대기 관계와 livelock을 실행 순서로 설명하기.
3. **MLFQ의 누적 CPU 사용량:** I/O를 요청할 때마다 사용량을 초기화하면 안 되는 이유.
4. **개념 구분:** syscall과 interrupt, hold and wait와 no preemption, 스레드 공유 자원과 CPU 자원.

스케줄링 계산은 전부 정확했습니다. 동기화 문제는 결과만 쓰기보다 ‘누가 무엇을 소유하고 무엇을 기다리는지’를 함께 적으면 설명형 문항의 점수를 더 확보할 수 있습니다.
