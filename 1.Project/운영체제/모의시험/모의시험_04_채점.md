## 상세 채점·해설

### 1. 프로그램·프로세스·스레드: 9.25 / 10점

**(가) 4 / 4점.** 컴파일러→어셈블러→링커 순서, 각 중간 파일과 `.data`·`.bss`가 모두 정확합니다. 1회에서 틀렸던 부분을 바로잡았습니다.

**(나) 2.25 / 3점.** 별도 PC·레지스터에 각 0.75점, 공유 가상 주소공간에 0.75점입니다. `kernel space`는 공유 가상 주소공간과 독립적인 프로세스 공유 자원 두 번째 예로 보기 어려워 해당 0.75점은 부여하지 않았습니다. 커널 주소 매핑이 공유될 수 있다는 사실과 별개로, 이 문제에서는 **가상 주소공간, 열린 파일 자원**처럼 서로 다른 자원을 제시하면 명확합니다. 각 스레드의 커널 스택까지 같은 것이라고 이해하지 않도록 주의하세요.

**(다) 3 / 3점.** I/O 대기 중 Blocked, 완료 후 Runnable, 스케줄러가 선택하면 다시 실행한다는 흐름이 정확합니다. PC 등의 저장 상태 설명에서 `sbp`는 문맥상 스택 관련 레지스터를 뜻한 것으로 보았으며, 문제의 채점 대상인 상태 변화에는 영향을 주지 않았습니다.

### 2. RR와 CFS 모델: 12 / 15점

**(가) 4 / 6점.** Turnaround=(8,4,9), response=(0,2,4)는 모두 정확해 각 2점입니다. 요구한 **실행 구간**이 빠져 2점 감점했습니다.

정답: `A[0,2) → B[2,4) → C[4,6) → A[6,8) → C[8,9)`.

**(나) 4 / 5점.** 선택 A→B, 최종 vruntime=(24,23)은 맞습니다. 증가량도 A는4, B는2로 정확하게 반영한 것으로 인정했습니다. 다만 문제는 **각 실행 후** 상태를 요구했는데, 첫 실행 직후 `(24,21)`이 빠져 1점 감점했습니다.

- A 실행 후: `(24,21)`
- B 실행 후: `(24,23)`

**(다) 4 / 4점.** Slice=3ms, 순환시간=24ms 모두 정확합니다.

### 3. MLFQ의 실행 추적: 8.5 / 10점

**(가) 5.5 / 7점.** 첫 A 실행 2와 마지막 A 실행 4, 시각2의 Q1 이동은 맞습니다. 하지만 **B의 총 CPU 요구량은 1**이므로 2만큼 실행하면 안 됩니다. Quantum은 최대 연속 실행량이며, 작업이 먼저 끝나면 즉시 CPU를 반환합니다.

정답: `A[0,2) → B[2,3) → A[3,7)`.

부분점수: 첫 A 구간 1.5점, B 구간 0점, 마지막 A의 순서·실행량 1.5점, Q1 이동 2.5점. B의 시간 오류로 뒤 시각이 밀린 부분을 마지막 A 구간에서 중복 감점하지 않았습니다.

**(나) 3 / 3점.** 낮은 우선순위 작업의 starvation 완화와 작업 성격 변화 후 우선순위 회복을 정확히 설명했습니다.

### 4. 락의 정확성과 대기: 8 / 10점

**(가) 4 / 4점.** 확인과 설정 사이에 선점되어 두 스레드가 모두 진입하는 실행 순서를 정확히 설명했습니다.

**(나) 2 / 4점.** `guard를 풀기 직전 setpark`라는 위치는 맞아 2점입니다. 다만 문제에서 함께 요구한 **알림 소실 실행 순서**가 빠져 해당 2점은 부여하지 않았습니다.

보완: 대기자 큐 등록→guard 해제→소유자가 unpark→대기자가 park→깨우는 알림을 놓쳐 잠듦. setpark는 그 unpark를 기억해 다음 park가 잠들지 않도록 합니다.

**(다) 2 / 2점.** Guard가 타이머 인터럽트·context switch 자체를 금지하지 않는다는 설명이 정확합니다. 다른 스레드는 같은 guard를 사용하는 보호 구간을 동시에 실행하지 못한다는 뜻으로 인정했습니다.

### 5. 세마포어·공정성·진행: 12 / 15점

**(가) 2 / 5점.** Consumer의 full·empty 역할과 연산 방향이 뒤바뀌었습니다.

정답:

`wait(full) → wait(mutex) → get → post(mutex) → post(empty)`

- `full`: 소비 가능한 데이터 수. Consumer가 **데이터가 있을 때만 get**하도록 합니다.
- `empty`: 생산 가능한 빈 슬롯 수. Producer가 **빈자리가 있을 때만 put**하도록 합니다.
- `mutex`: 공유 버퍼 조작의 상호배제입니다.

Mutex 획득 후 get하고 해제한다는 부분에 순서 배점 중 1점, mutex 역할에 1점을 인정했습니다. 나머지 순서 1점과 full·empty 역할 각 1점은 감점했습니다.

이름을 ‘무엇을 막는가’로 외우기보다 **무슨 허가를 몇 개 가지고 있는가**로 이해하세요. Consumer는 데이터 허가 full을 소비하고, 빈자리 허가 empty를 반환합니다.

**(나) 4 / 4점.** Reader가 계속 겹쳐 들어오면 write_lock이 writer에게 돌아오지 않는다는 설명이 정확합니다.

**(다) 6 / 6점.** Livelock, 즉시 재시도 대신 대기·양보하는 완화책, 전역 순서로 circular wait를 제거한다는 답을 모두 인정했습니다. 다만 두 스레드가 같은 시간만 기다리면 재충돌할 수 있으므로 **무작위 backoff**라고 쓰면 더 분명합니다. 단순 yield도 모든 실행에서 진행을 보장하지는 않습니다.

### 6. Amdahl의 역산: 10 / 10점

세 답이 모두 정확합니다. 식 누락에 대한 추가 감점은 하지 않았습니다.

- **(가) 4 / 4점:** `1/2.5 = S+(1-S)/4`에서 **S=0.2**.
- **(나) 3 / 3점:** `0.2+0.8/N ≤ 1/4`에서 **N≥16**, 최소 **16코어**.
- **(다) 3 / 3점:** `1/(0.05+0.95/8) = 160/27 ≈ 5.93배`.

3회에서 불안정했던 Amdahl 계산은 이번에 모두 맞았습니다. 이후에는 추가 비용이나 일부 병렬 영역의 코어 수 제한이 들어간 경우로 확장하면 됩니다.

### 7. MQMS의 부하 분산 추적: 16 / 20점

**(가) 6 / 8점.** 두 CPU의 유용 실행 구간은 정확합니다(4점). CPU0의 완료시각12를 통해 전체 makespan도 맞게 제시한 것으로 인정합니다(2점). 다만 CPU1의 개별 완료시각4를 전체 makespan과 구분하세요.

합산 idle은 **12가 아니라 8**입니다(0 / 2점).

- CPU0: A\[0,8), B\[8,12), idle=0.
- CPU1: C\[0,2), D\[2,4), idle\[4,12), idle=8.
- 전체 makespan=12, 합산 idle=0+8=8.

**(나) 6 / 8점.** 시각4에 CPU1이 B를 가져가 \[4,8)에 실행하는 순서와 전체 makespan8은 정확합니다(구간4점+완료시각2점). 합산 idle은 **8이 아니라 0**입니다(0 / 2점). 두 CPU 모두 \[0,8) 동안 계속 유용한 작업을 실행합니다.

검산 공식:

`합산 idle = 코어 수 × 전체 makespan - 총 유용 CPU 시간`

이 문제는 별도 비용이 없으므로 그대로 적용할 수 있습니다. 총 유용시간은 `8+4+2+2=16`입니다.

- 이동 전: `2×12-16=8`.
- 이동 후: `2×8-16=0`.

이동 비용이 있는 문제에서는 idle과 비용 구간을 구분해야 합니다.

**(다) 4 / 4점.** 다른 CPU의 큐에 접근할 때의 동기화 경합과 cache affinity 손실을 모두 설명했습니다. 답안의 ‘concurrency 이슈로 생기는 시간’은 문맥상 큐 보호를 위한 경합·직렬화 비용으로 인정했습니다.

### 8. 멀티코어 설계 판단: 7 / 10점

**(가) 3 / 4점.** “항상 보호가 필요 없다”는 주장이 틀렸다는 판단과 큐 보호 필요성을 인정했습니다. 다만 보호의 핵심 이유인 **원래 큐 소유 CPU와 stealing CPU가 같은 큐를 동시에 수정할 수 있음**을 명확히 쓰지 않아 1점 감점했습니다. Work stealing 빈도를 줄이는 것만으로 큐의 정확성이 보장되지는 않습니다.

**(나) 3 / 3점.** CPU0의 부하를 CPU1로 분산하면서 cache에 없던 데이터를 다시 가져오는 비용이 발생한다는 예가 맞습니다. CPU0에 작업을 유지하면 locality는 좋지만 부하 분산 기회를 잃는다는 점까지 덧붙이면 더 명확합니다.

**(다) 1 / 3점.** Data parallelism 분류는 맞습니다(1점). 하지만 ‘두 작업이 data independent’하다는 것은 분할 작업을 병렬로 실행할 조건이며, 질문의 **병합 시작 전 완료 보장**에 대한 답은 아닙니다(0 / 2점).

정답 보완: **필요한 모든 부분 결과가 완료되고 병합 스레드에서 관측 가능해야 합니다.** Join 또는 완료 세마포어 등의 동기화로 보장합니다.

## 이번 결과에서의 복습 우선순위

1. **Consumer의 세마포어 방향:** full을 기다리고, 소비 후 empty를 돌려줍니다.
2. **멀티코어의 시간 측정:** 전체 makespan, 각 CPU의 완료시각, 합산 idle을 구분합니다.
3. **병렬 작업 완료 동기화:** 독립적으로 실행할 수 있다는 것과 결과 병합을 시작해도 된다는 것은 다릅니다.
4. **요구 항목 확인:** 실행 구간, 각 실행 후 중간 상태, 오류가 생기는 실행 순서가 빠지지 않도록 답을 확인합니다.

컴파일·링크 과정과 Amdahl은 개선이 확인됐습니다. RR의 결과 계산과 락 실패 순서도 정확합니다. 현재는 새 개념을 더 외우기보다 세마포어 허가의 방향, 시간 지표의 정의, 완료 동기화 조건을 정확히 적용하는 연습이 효과적입니다.
