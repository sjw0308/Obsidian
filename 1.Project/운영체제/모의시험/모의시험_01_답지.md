4. MLFQ RR
	1. time slice를 줄이면 response time은 줄어들지만 더 많은 context switch로 전환 비용이 증가한다
	2. 나중에 들어온 작업들이 계속 가장 높은 우선순위를 배정 받기 때문에 처음에 batch작업이었다가 나중에 interactive한 작업이 되어도 우선순위를 높이지 못하고 starving하는 문제가 발생하여 중간중간 priority boost를 통해서 그런 작업들의 우선순위를 높여주어야 한다.
	3. CPU사용시간/timeslice 를 구해서 해당 값이 1에 가까우면 우선순위를 낮추는 방법을 사용할 수 있다.
5. Race condition
	1. A 스레드가 x를 load, add후 schedule out 됨 -> B 스레드가 x ++ 작업을 모두 실행함 -> A가 다시 schedule in되어서 store작업을 실행
	2. 1, 2가 가능하고 load, add, store 전체가 critical section이다. 
	3. PC와 register, CPU와 memory
6. lock

	   while(TestAndSet(&l->flag,1)==1);
	   }
	   unlock(lock_t* l){
	   TestAndSet(&l->flag, 0);
	   }
	   ```
	2.  기존 TAS 락은 unlock된 이후 spin상태로 기다리는 thread중 운좋게 schedule된 애를 실행하기 때문에 운이 안좋으면 starving될 수 있지만, ticket lock은 queue를 통해서 기다리는 thread 중 가장 오래 기다린 thread를 실행시켜주기 때문에 더 공정하다.
	3. 아니다. 같은 critical section을 공유하는 다른 thread가 다른 CPU에서 실행될 수 있기 때문이다.

8. deadlock
	1. L1, L2가 mutex이고(1번조건), T1, T2는 잡고있는 L1, L2를 놓을 수 없으며(2번조건) 서로 Cycle을 이루며 기다리고 있다.(4번조건) 또한 해당 lock을 강제로 회수할 수 없다. (3번조건)
	2. 모든 전역 락에 순서를 부여하고 각 thread에서 해당 lock을 해당 순서에 맞추어서 부여하면 deadlock이 생기지 않는다
	3. 너무 많은 부분의 코드를 재실행 할 수 있어서 overhead가 크고, 그 코드 부분에 잡았던 melloc등을 trylock 실패시 free해주어야 한다.
