
1. 프로세스
	1. C파일 -> 컴파일러 -> .s 어셈블리 파일 -> 어셈블러 -> .o 오브젝트 파일 -> 링커 (+static library) -> executable file
	   초기화된 전역변수는 .data에 미초기화된 전역변수는 .bss에 존재한다
	2. 공유: 가상 메모리 공간, kernel space
	   별도유지: PC, register
	3. IO 요청 -> trap -> kernel stack에 프로세스의 pc, sbp등 진행상태 저장 -> IO처리(in blocked state) -> IO완료(interrupt) -> Runnable state로 변경되어 바로 실행되지 않고 다음에 schedule된다면 실행된다.
2. RR, CFS
	1. turnaround: A=8, B=4, C=9 / response: A=0, B=2, C=4
	2. 처음 두 선택은 차례로 A, B이다 실행 후 vruntime은 A=24, B=23이다.
	3. slice는 3ms, 순환시간은 24ms이다.
3. MLFQ
	1. 전체 실행순서는 A 2 -> B 2 -> A 4이고, 시각 2 직후 A는 Q1이다. 
	2. 우선순위가 낮은 작업의 starvation 문제를 해결할 수 있고, batch였다가 나중에 interactive작업으로 바뀐 작업의 우선순위도 바꿀 수 있다. 
4. lock
	1. 처음 lock을 잡는 A가 while문을 지난 후 flag변형 전에 다른 B로 context switch되면 아직 flag=0이므로 B도 lock에 진입하고, 이후 A가 다시 돌아와서 flag=1을 재설정 하면서 lock에 A, B가 모두 진입함
	2. guard를 풀기 직전에 setpark을 실행
	3. timer interrupt나 context switch가 금지되지는 않지만 다른 thread들이 해당 부분을 실행할 수는 없다. 
5. semaphore
	1. empty wait -> mutex wait -> get -> full post -> mutex post, full은 buffer가 다 찼는데 producer가 buffer에 넣는 것을, empty는 buffer가 empty인데 consumer가 뺴려고 하는 것을, mutex는 critical section이 동시에 실행되는 것을 막는다. 
	2. reader의 추가가 계속 가능하기 때문에 reader가 계속 들어오면 write_lock이 writer에게 돌아오지 않고 계속 이어진다. 
	3. 두 thread가 서로 하나의 lock을 잡았다가 풀기를 반복하는 live lock문제가 발생한다. 이를 해소하기 위해선 즉시 재시도 하지 않고 약간 기다리거나 schedule out하는 해결방법이 있다. 
	   모든 락을 전역 순서대로 잡으면 circular wait조건을 제거할 수 있다.

7. MQMS
	1. CPU0: A8 -> B4, makespan=12 / CPU1: C2 -> D2, makespan=4 / 합산 idle=12
	2. CPU0: A8 makespan=8 / CPU1: C2 -> D2 -> B4, makespan=8 / 합산 idle=8
	3. 두 CPU가 같은 queue에 접근하기 때문에 lock을 걸어서 생기는 concurrency이슈로 생기는 시간 + cache affinity가 떨어져서 생기는 cache miss로 인한 overhead
8. multi core
	1. 아니다. work stealing은 가끔으로 하고 큐를 보호해야 concurrency로 시간이 늘어나는 것을 가능한 막을 수 있다. 
	2. CPU0가 일이 많다고 하던 일 A를 CPU1이 뺏어가면, CPU1의 cache에는 A에 관한 data가 없기 때문에 cache affinity가 떨어진다. 
	3. data parallelism, 두 작업이 data independent해야 한다.
